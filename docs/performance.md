# Performance

## Diagnostics HUD

`src/dev_tools/` uses Bevy's built-in `bevy_dev_tools::diagnostics_overlay` (`DiagnosticsOverlay`/`DiagnosticsOverlayPlugin`) — a draggable, collapsible on-screen window, enabled via the `bevy_dev_tools` Cargo feature. Only present while `GameState::Playing` (spawned `OnEnter`, despawned `OnExit`), since that's the only demanding scene right now.

Two separate overlay windows (the API supports spawning as many as you like):

**"Performance"** window:
- **FPS** and **frame time** (`FrameTimeDiagnosticsPlugin`)
- **Loaded triangle count** (`loaded_tris`) — a custom diagnostic, updated every frame by summing `mesh.indices().len() / 3` across *every* `Mesh3d` entity in the scene (chunks, sky dome, sun cube), **regardless of `ViewVisibility`**. Deliberately not named "visible" or "rendered": frustum/occlusion culling is a per-*entity* bounding-box test (see below), not a per-triangle one, so a mesh that's 99% off-screen still contributes its full triangle count here. For "what's actually being drawn this frame," use `visible_tris` in the Chunks window instead.
- **Entity count** (`EntityCountDiagnosticsPlugin`) — see "Why the entity count looks high" below before assuming this number means what it looks like it means
- **Process CPU / memory usage** (`SystemInformationDiagnosticsPlugin`) — "how much resources it's using"
- **Grid X/Y/Z** and **Local X/Y/Z** (the player's position in the world grid, `playing::GridPos`/`GridPos::local_offset`) — confirmed working correctly, so **currently hidden** from the overlay to reduce clutter (`SHOW_COORDINATE_HUD = false` in `src/dev_tools/mod.rs`). The diagnostics are still registered and the update system still runs every frame either way — flipping the const back to `true` is the entire re-enable path, nothing was deleted. The debug wireframe box that used to be drawn around the player's current grid cell has been removed entirely (it was a gizmo-only debug aid, not tied to the coordinate readout above).

**"Chunks (3x3 near player)"** window: anchored to the **top-right** of the window (`src/dev_tools/mod.rs`'s `setup`, via a `Node` override inserted right after spawning the overlay) so it no longer overlaps the "Performance" window, which stays at its default top-left position. Three numbers up front, deliberately exact and unambiguous:

- `loaded_chunks` — the total number of chunk entities that currently exist, visible or not (81 in normal streaming, exactly 4 when `world::DEBUG_FIXED_CHUNK_GRID` is on). This is the number that answers "is chunk generation actually limited right now" — distinct from `loaded_tris` in the Performance window above, which sums *every* `Mesh3d` in the scene (chunks **and** the sky dome/sun cube).
- `visible_chunks` / `visible_tris` — aggregated across *every* loaded chunk (not just the nearby 3x3 breakdown below), counting a chunk only if `ViewVisibility` says it's actually being drawn this frame.

Below that, a 3×3 per-chunk triangle breakdown (frustum-/occlusion-culled chunks read exactly 0, not just a smaller number) — centered on the player's current chunk normally, or on the origin when `DEBUG_FIXED_CHUNK_GRID` is on (so the slots line up with the fixed 2x2 debug set instead of going stale once the player flies away from it). This directly answers "is culling doing anything": look away from a loaded chunk and its number should visibly drop to 0, rather than having to trust the aggregate triangle count alone.

**Important nuance confirmed while debugging with `DEBUG_FIXED_CHUNK_GRID`**: culling is a per-*entity* bounding-box (`Aabb`) test against the camera frustum, not a per-triangle one. If even a sliver of a chunk's 32x32x32 bounding box pokes into the frustum, that entire chunk counts as "visible" and its *whole* triangle total is added to `visible_tris` — even if 95% of what's on screen for that chunk is empty sky and only a corner is actually poking into view. Seeing a chunk's full triangle count (e.g. ~800) attributed to what looks like a single sliver on screen is expected, correct behavior, not a bug — the GPU still only rasterizes the pixels the geometry actually covers; the "wasted" triangles outside the visible slice are cheap to clip in hardware and are not the FPS bottleneck.

## Why the entity count looks high

At `RENDER_DISTANCE = 4` the scene has ~82 `Mesh3d` entities (81 chunks + 1 sun cube), 1 camera, 1 light, and ~29 HUD UI nodes — call it ~115 entities you'd reasonably expect. The HUD reports something like 520+. The gap was investigated directly (temporarily enabling bevy's `debug` Cargo feature — kept on since it's generically useful for exactly this kind of investigation — to get real component type names instead of `<Enable the debug feature to see the name>` placeholders, then dumping every entity's component archetype):

- **~320 entities are `bevy_ecs::resource::IsResource`** — Bevy 0.19 stores every registered `Resource` internally as its own entity. This is pure engine bookkeeping present in *any* Bevy app regardless of scene content: none of these entities have `Transform`, `Mesh3d`, or `Visibility`, so they're never touched by transform propagation, culling, or rendering. Zero per-frame cost.
- **~82 are `Observer` entities** — one per mesh's material/asset-change observer registration, also Bevy-internal, also with no render-path involvement.
- The sky dome was suspected as the cause at one point; it wasn't. Confirmed by direct A/B measurement (`SKY_DOME_ENABLED` toggle in `src/playing/mod.rs`): entity count and triangle count were essentially identical with it on vs. off (521 vs 522 entities, ~37,900 triangles either way) — expected, since it's a single ~20-triangle mesh and mathematically could never account for hundreds of entities.

Bottom line: the entity count Bevy reports is dominated by internal bookkeeping that has no bearing on FPS. The numbers that actually matter for performance are triangle count and draw calls, both of which come entirely from the chunk terrain (see below).

## Optimizations Made (and why)

- **`[profile.dev]` opt-level override in `Cargo.toml`** — found while investigating why FPS stayed in the teens even with `DEBUG_FIXED_CHUNK_GRID` on (4 chunks loaded, 1 visible, ~800 trivial triangles — nowhere near enough geometry to explain 13 FPS on any real hardware). The project had no dev-profile override at all, meaning `cargo run`'s default dev profile compiled *Bevy itself* (ECS, renderer, wgpu) fully unoptimized — a well-known, officially-documented Bevy gotcha, not something specific to this project's code. `opt-level = 1` for our own crate (keeps iterative compiles fast) plus `opt-level = 3` for every dependency (what actually matters for runtime FPS) is Bevy's own recommended fix. First build after this change recompiles all dependencies once; every build after that stays fast. If FPS is still low after this, the bottleneck is something else and worth investigating fresh — this was suspected as *a* cause, not confirmed as *the* cause, until tested.
- **One entity per chunk, not one per block** (`src/playing/world/`, see `docs/world-generation.md`): the original flat placeholder ground spawned 1024 individual block entities, confirmed (via a temporary debug breakdown) to be the dominant cause of a reported 7 FPS / 1455-entity reading. Replaced by a chunked pipeline where each ~32x32x32 chunk is face-culled and greedily merged into a single mesh, single entity — ~81 chunk entities at the default render distance instead of 1024+ loose block entities for a much smaller area.
- **Sky dome is a level-0 icosphere (~20 triangles), not a subdivided sphere** (`src/playing/mod.rs`): `SkyMaterial` colors per-fragment from the view direction, not per-vertex, so a low-poly dome looks pixel-identical to a high-poly one — extra triangles would only cost vertex/rasterization time for zero visual gain.
- **`SkyMaterial` disables its prepass and shadows** (`src/playing/sky.rs`, `enable_prepass() -> false`, `enable_shadows() -> false`): it's a simple unlit fragment shader; nothing needs its depth/normal prepass output or its shadow contribution.
- **The sun's `DirectionalLight` has `shadow_maps_enabled: false`** (`src/playing/sun.rs`): revisit once terrain has enough height variation for shadows to matter visually.
- **Chunk generation/meshing is budgeted, not all-at-once** (`CHUNKS_PER_FRAME` in `src/playing/world/manager.rs`): spreads the initial ~81-chunk load-in (and any large re-load from fast movement) across multiple frames instead of a single stall.
- **Cross-chunk face culling** (`docs/world-generation.md`): chunk data is padded by one block on every horizontal side so the mesher can see the real neighboring terrain at chunk boundaries instead of assuming air — removes the extra, un-mergeable faces that used to render along every chunk seam.
- **GPU occlusion culling enabled** (`DepthPrepass` + `OcclusionCulling` on the `Camera3d`, `src/playing/mod.rs`): Bevy 0.19 ships real two-phase hierarchical-Z occlusion culling (`bevy::render::occlusion_culling`) — already included in `DefaultPlugins`, just off by default. With it on, chunks that are fully hidden behind other opaque terrain (e.g. the far side of a hill) don't even get their vertices transformed, on top of the frustum culling Bevy already does automatically for every mesh's computed AABB.
- **Down-facing (-Y) mesh pass skipped entirely** (`src/playing/world/mesher.rs`): the generator only ever produces "solid below the surface height, air above" columns — no caves, no overhangs — so a down-facing face (solid with air directly below) can only ever occur at y=0, the world floor, which the camera can never get under to see. Free win: half the Y-axis mesh work, skipped unconditionally, revisit if caves/overhangs are ever added.
- **Height quantization instead of flattening the terrain** (`QUANTIZE_STEP` in `src/playing/world/generator.rs`): the first attempt at reducing triangle count lowered the noise amplitude/frequency directly, which worked but made the terrain visually boring — a regression. The actual constraint the mesher can't get around is that **two faces only merge into one quad if they sit at the exact same integer height** (a quad is one flat plane); a terrain with small height changes that happen often merges just as badly as one with big dramatic swings, since either way most neighboring columns don't share a height. Quantizing the surface height to steps (`QUANTIZE_STEP = 4`) creates real flat plateaus the mesher can merge, while the underlying noise scale/height went back to being large and dramatic — the terracing reads as a deliberate stylistic choice rather than a bug, and gets the mergeability benefit without sacrificing visual variety.
- **Chunk-switch hysteresis** (`SWITCH_MARGIN` in `src/playing/world/manager.rs`) — **fixed a real bug**, not just an optimization: standing near (or moving through) an exact chunk boundary could flip the computed `ChunkPos` back and forth every single frame (ordinary floating-point movement noise is enough), and *each flip re-evaluated the entire 9x9 render window*, despawning and regenerating most of the chunks along the shifted edge — every frame, for as long as the flickering continued. This is what caused FPS to crater specifically near terrain/looking at the ground: that's exactly where a player's position is likely to sit near a boundary. Fixed with hysteresis: once a chunk is confirmed, the player must move `SWITCH_MARGIN` blocks *past* its edge (not just barely across it) before a switch is recognized, so being near a boundary no longer thrashes the render window.
- **One shared material handle for every chunk, not one per chunk** (`ChunkManager::material` in `src/playing/world/manager.rs`): every chunk looks identical today (flat debug green via vertex colors), but `load_pending_chunks` used to call `materials.add(...)` once per chunk anyway — 81 separate `StandardMaterial` assets for a single visual result. Now the first chunk spawned lazily creates one material and every subsequent chunk reuses the same `Handle<StandardMaterial>`. Directly shrinks the same kind of per-asset bookkeeping (observers, asset-change tracking) documented in "Why the entity count looks high" above. Revisit once real per-block-type materials/textures exist and chunks stop being visually identical.

## Not Yet Done (candidates if profiling says they're needed)

- Async/threaded chunk generation (currently main-thread, just budgeted per-frame).
- Reduce MSAA if edge aliasing cost matters more than jaggies — not changed since it's a visible quality trade-off, not an invisible win.
- Per-block-type textures/atlasing once real block types exist (currently flat vertex-color debug green).
