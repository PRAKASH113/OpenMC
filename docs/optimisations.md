# Optimization Roadmap

This maps techniques (from `docs/optimisation.txt`'s video, and whatever the user finds and adds) onto *this* engine's actual state — what's done, what's next, what's been deliberately declined and why. Kept updated as work happens, not just planned in advance.

## Where we already are relative to the video

The video's steps 1–3 (chunking, face culling, greedy meshing) and part of step 7 (skip faces that can never be seen) are **already done**, via a different path than the video took to get there:

- **Chunking, one entity per chunk** (`src/playing/world/manager.rs`) — video's step 1.
- **Face culling, via per-column bitmasks precomputed once per column** (`mesher.rs`) — video's step 1 (triangle reduction). Originally the file's own doc-comment *claimed* `column & !(column >> 1)` computed a whole column's face visibility in one shot, but the code actually re-derived two shifts per `(x, y, z)` triple (32,768 times per chunk) instead of once per column (1,024 times). Fixed: `up_faces`/`down_faces` (Y axis) and `right_faces`/`left_faces`, `front_faces`/`back_faces` (X/Z axes) are now precomputed once per column with exactly this trick, and the per-level mask-building loop just reads the precomputed bit. Output is identical (verified algebraically, not just by inspection: shifting right naturally fills the vacated top bit with 0, which is exactly "nothing above the last block" — the same edge-case behavior the old bounds-checked version had, with no special-casing needed).
- **Greedy meshing, already merged in *both* directions per face** (`mesher.rs::greedy_merge`) — this is actually past where the video is at its step 3 (which can only merge one direction until step 6 frees up bits by moving face-direction data into an SSBO). We aren't bit-packing vertices at all right now, so we never had that constraint — full 2D rectangle merging was "free" to implement from day one.
- **Skip the entire down-facing (−Y) mesh pass** (`mesher.rs::mesh_axis_y`) — conceptually the same idea as the video's step 7 (don't generate triangles that can never be seen), but done at generation time via a static fact about our generator (no caves ⇒ no visible down-faces), not via per-chunk-per-direction mesh splitting.
- **Cross-chunk padding for boundary face culling** (`chunk.rs`'s `PADDING`/`PADDED_SIZE`) — not in the video (their world is one contiguous buffer, not separately-streamed chunks), but solves the same "don't render a face that's actually touching solid neighbor geometry" problem chunk streaming introduces.
- **GPU hierarchical-Z occlusion culling** (`DepthPrepass` + `OcclusionCulling` on the camera, `src/playing/mod.rs`) — this is Bevy's built-in equivalent of (and more general than) the video's step 7 direction-based culling: it culls *any* fully-hidden geometry, not just backfaces relative to 6 fixed directions.
- **Vertices already indexed per quad, not per triangle** (`mesher.rs::MeshBuilder::push_quad`): each merged quad stores 4 vertices + 6 indices (2 triangles), not 6 separate vertex records — this *is* the index-buffer sharing a naive "36 vertices per cube" mental model is missing. See "Vertex sharing" below for why it doesn't extend further than this.
- **The 2D rectangle merge itself is now bitwise too, not just face visibility** (`mesher.rs::greedy_merge`) — ported from studying `cgerikj/binary-greedy-meshing` (cloned into `ref/` temporarily to read, deleted once done — see below). The old version scanned a heap-allocated `Grid` of `bool`s cell-by-cell to grow `width`/`height` and mark cells "visited." The new version represents each layer as `[u32; CHUNK_SIZE]` (one word per row — no heap allocation at all, unlike `Grid`'s two `Vec<bool>` allocations per layer) and uses `trailing_zeros()` (`bsf`/`ctz`, one hardware instruction) to find a run's width, then clears an entire consumed rectangle with `consumed[row] |= run_mask` instead of a nested loop of individual writes. Simplified relative to the reference: it doesn't track per-voxel-type equality *inside* the merge loop the way the reference does — now that there are multiple block types (stone/grass/sand/water, see `docs/world-generation.md`), that's handled by splitting each level's visibility mask into one `Mask` per type *before* calling `greedy_merge`, so two types are never even candidates for the same merge pass, and this function stays exactly as simple as when there was only one type. **Verified correct**, not just by inspection: a property-based test suite (`mesher.rs`'s `#[cfg(test)] mod tests`) checks, across hand-built edge cases and 500 random masks, that every emitted rectangle only covers originally-set cells, no two rectangles overlap, and every set cell ends up covered by exactly one rectangle, plus a dedicated test confirming two different block types never end up in the same merged quad — `cargo test` passes all of them.

So the low-hanging fruit the video spends its first half on is already in place, and both halves of "binary greedy meshing" (face visibility *and* the merge step itself) are now actually bitwise, not just described that way in a comment. What's left is the video's second half: **shrinking what a vertex costs**, which we haven't touched — we're using Bevy's stock `Mesh::ATTRIBUTE_POSITION`/`ATTRIBUTE_NORMAL`/`ATTRIBUTE_COLOR`, each a full `f32` vector per vertex, no packing at all.

## Vertex sharing — why it stops at "per quad," not "per cube" or "per neighbor"

A cube's 8 corners *can* share position data across its 6 faces, but not a complete vertex (position + normal + color together) — each face needs its own normal at that corner, and Bevy's own `Cuboid` primitive generates 24 vertices for exactly this reason (confirmed by reading `bevy_mesh`'s cuboid builder directly), not 8. Sharing a full vertex across faces with different normals would average/interpolate the normal at the shared corner — smooth shading, which would round off every block edge instead of keeping the sharp Minecraft-style look. Sharing between *neighboring* blocks/chunks doesn't apply either: face culling already removes the touching faces between two solid blocks, so in the common case there's no shared visible geometry there to begin with. What we already do — 4 vertices/6 indices per merged quad — is the actual extent of useful vertex sharing for this flat-shaded style.

## Investigated and declined: packed vertex format for memory (600MB reading)

The user reported 600MB process memory and initially proposed packed/bit-compressed vertices as the fix. Measured before doing anything: at `RENDER_DISTANCE = 4` with 105,484 triangles on screen, current vertex+index data across *every* loaded chunk totals roughly **9.25MB** (~1.5% of 600MB) — even packing every vertex to a single `u32` couldn't move a 600MB reading, because chunk geometry was never where that memory was going. The 600MB is almost certainly Bevy/wgpu's own baseline (Vulkan driver, swapchain, asset server, shader caches) — normal for a Bevy dev-profile build, not something that scales with terrain drawn. **Declined for now**: still a legitimate technique (matters at much larger render distances, or once GPU vertex-fetch bandwidth is the bottleneck rather than memory), and still described below in case it's picked back up later, but it would not have fixed the reported problem, so implementing it now (a substantial rewrite — see the "why this got harder" note in the item below) wasn't worth the risk. If total memory needs to come down, the next step is finding what's *actually* using the 600MB, not assuming.

## Planned, in priority order (not currently being worked)

### 1. Packed vertex format (video steps 2–3)

Replace `[f32; 3]` position + `[f32; 3]` normal + `[f32; 4]` color per vertex with a single packed integer attribute, matching the video's scheme adapted to our data:

- Position: 6 bits per axis (`CHUNK_SIZE = 32` needs exactly 6 bits, unlike the video's bit-squeezing exercise — we can use the same width for all three axes without extra cleverness).
- Normal: our normals are only ever one of 6 axis-aligned directions (this is already true today — `mesher.rs` never emits an oblique normal) — 3 bits, reconstructed in a custom vertex shader.
- Block/face color: now that there are real per-block-type colors (`chunk::BlockId`/`block_color`, stone/grass/sand/water — see `docs/world-generation.md`), a small block-type ID (`BLOCK_TYPE_COUNT` is currently 5, needs 3 bits) fits in a handful of bits the same way the video packs a texture ID, with the actual color looked up from a small array/uniform in the shader rather than carried per-vertex as `[f32; 4]`. Once real textures exist later, the same ID field becomes a texture index instead — no format change needed twice.

This requires a custom `Material` (we already have a precedent for this — `SkyMaterial` in `src/playing/sky.rs`, though that one only overrides the *fragment* shader) with a custom WGSL vertex shader that unpacks the bitmasked attribute, instead of the current `StandardMaterial`.

**Why this item got more expensive since it was first scoped**: back then there was no ambient light, no fog, no shadows on terrain. Now there are all three, and `StandardMaterial`'s automatic pipeline can't be mixed with a custom vertex attribute layout — its default shader hard-codes reading the standard position/normal attributes. Doing this now means either (a) hand-assembling a `pbr_types::PbrInput` and calling Bevy's own `pbr_functions::apply_pbr_lighting` + `bevy_pbr::fog::linear_fog` from a custom shader to keep full fidelity (verified these are real, callable WGSL functions — but `PbrInput` has ~20+ fields, easy to get subtly wrong, and I can't visually test a shader bug myself), or (b) accepting terrain loses real-time shadow-receiving and reproducing ambient+directional diffuse by hand (lower risk, smaller task, visible regression). Also still needs the `Aabb`-component gotcha noted before: dropping `Mesh::ATTRIBUTE_POSITION` breaks Bevy's automatic per-entity bounding-box computation (used by frustum/occlusion culling) unless a fixed `Aabb` is attached manually per chunk.

### 2. Quad instancing (video step 3)

Once vertex data is packed, switch from 4-vertices-times-6 (24, after greedy merging usually far fewer, but still duplicated corners) per quad to a single 4-vertex base quad mesh drawn via instancing, with one packed `u32`/`u64` of per-instance data (position + size + direction) instead of unique per-vertex data for every quad. Meaningful memory win on top of #1, but only worth doing once #1 exists to instance *from* — packing and instancing are naturally the same piece of work split in two.

Confirmed this is a real, proven approach, not just a video's suggestion: `cgerikj/binary-greedy-meshing` (studied for item 5's merge-step fix, above) does exactly this in production — one `u64` per quad via "vertex pulling" (no traditional vertex buffer at all; the vertex shader reconstructs the 4 corners procedurally from the packed value using the vertex/instance index), 8 bytes per quad total.

### 3. Backface / per-direction chunk meshes (video step 5) — **needs a scope decision first**

The video splits each chunk into 6 meshes (one per face direction) so it can skip drawing meshes facing away from the player before they ever reach the vertex shader. Doing the same here would mean **up to 6 entities per chunk instead of 1**, which directly conflicts with the "one entity per chunk, never one per block" rule from `docs/world-generation.md`. That rule was about *blocks*, not directions, so it's not automatically violated in spirit — but it's a real increase in entity count (81 chunks → up to 486 sub-mesh entities at the default render distance) that should be confirmed explicitly before building, the same way render-distance scope and the one-entity-per-chunk rule itself were confirmed up front. Also lower priority than it looks: Bevy's GPU occlusion culling (already on) already discards most geometry this would target, so the marginal win over what we already have is smaller here than it was for the video's raw-OpenGL renderer with no occlusion culling of its own.

### 4. Manual indirect draw batching + SSBO chunk positions (video step 4) — **stretch goal, likely skipped**

The video's biggest single win (12,000 → the jump from many draw calls to one) comes from hand-rolling `glMultiDrawArraysIndirect` plus a manually-managed SSBO of chunk world positions, replacing Bevy's own render graph with a custom one. Bevy already auto-batches draws that share a mesh + material, but our chunks are all *unique* meshes, so that auto-batching doesn't apply — matching the video exactly would mean building a bespoke GPU-driven rendering path inside Bevy's render graph (custom vertex/instance buffers spanning all loaded chunks, indirect draw buffer, per-draw SSBO lookup). This is a large, deep-in-the-renderer undertaking disproportionate to the other items here; only worth it if profiling after #1–#3 shows draw-call count (not triangle count or memory) is the actual bottleneck.

## Not from the video, still worth tracking (see `docs/performance.md`)

- Async/threaded chunk generation (currently main-thread, budgeted per-frame).
- Real per-block-type texture atlasing (currently flat per-type colors, see `docs/world-generation.md`) — feeds directly into the texture-ID bits in item 1 above.
- Skip generating/meshing chunks that are *deterministically* deep underground (below the lowest possible `surface_height - RENDER_DISTANCE * CHUNK_SIZE` or similar) without running the generator/mesher at all — right now they still get fully generated and meshed, just correctly produce an empty mesh and no spawned entity (see `docs/world-generation.md`'s "Vertical chunk stacking"). Not measured yet whether this is worth the complexity.

## Verification approach

Same method the user already established for the mesher itself: toggle the terrain wireframe (Shift+1, see `docs/world-generation.md`) and watch the HUD's triangle/entity counts (`docs/performance.md`) before and after each change, rather than trusting any of this by inspection alone.
